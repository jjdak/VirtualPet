# 小庭院下一阶段：自主行为与现成系统调研

## 方向重新评估（2026-10-26）

用户反馈：「类似的单机或者demo太多了，继续这个方向没有意义」。撤下默认继续扩展庭院 demo 和试装行为插件的下一步；先讨论项目是否存在值得投入的独特体验或研究问题。现有成果与调研保留供参考，下面实施路线不再自动执行。尚未决定关闭整个项目，也未选定学习、LLM 或其他替代方向。

2026-10-25。状态：一手资料与部分源码已核对；候选未安装、未在本机运行、未决定采用。当前可玩版本仍为 [S2 控制候选](S2_CONTROL_PASS.md)。

用户最新要求：「不一定要尽快做一个成品出来，我们可以多搜索资料，做好充分的调研。」因此，下一步先进行方案比较和有明确问题的验证，不以赶制下一段 demo 为目标。下面是研究建议，不代表用户已选择新玩法或技术栈。

## 1. 研究目标与当前底座

体验方向仍是安静的小世界，用户可以观察、干预、接管。要研究的是：她能否表现出持续的兴趣、有限的认知和可理解的反应，让用户愿意改变条件，再看看会发生什么。

当前已有：Godot 庭院与少女A、行走/转身/停步、有限脚部校正、手动接管、双视角，以及纸船被树枝挡住和解除阻挡的世界状态。当前去池边是目标跟随与碰撞失败处理，没有完整 NavMesh 绕路；移动树枝是导演操作，没有人物实际伸手清障。局部感知、事件记忆、真实 LLM 都尚未实现。

沿用 [LLM 反馈设计](LLM_FEEDBACK_DESIGN.md)：角色接收局部观察和执行结果，世界真相与角色认知分离。白板世界可以研究行为；不重新搭建整个引擎，不改写 Blender 原工程。

## 2. 最有价值的设计发现：让物品携带交互能力

Forbus 与 Will Wright 的原始技术笔记描述了一种对象中心设计：物品定义行为、可执行条件及能满足的需求，角色据此选择活动，而非把所有交互硬编码进中央角色脚本。这是历史设计经验，不是近期 LLM 成果，也不意味着可复制《模拟人生》的代码或资产。[原始笔记，2001](https://users.cs.northwestern.edu/~forbus/c95-gd/2001/Programming%20Objects%20in%20The%20Sims.pdf)

对本项目的推论：庭院中的池边、纸船、长椅可以分别声明可用活动、接近位置、前置条件、持续时间、取消方式和结果。人物只在已感知/已知的候选活动中选择。以后增加物品时，主要增加该物品的能力与动作适配，避免重写整个角色逻辑。

例如“观察纸船”可拆成：确认最后看见的位置 → 到达可观察位置 → 转向 → 停留 → 获得新观察。纸船是否卡住由世界碰撞决定；“她为什么愿意过去”由兴趣、近期事件或高层目标决定。这两部分分开后，规则与 LLM 可以共用执行器。

需要防止一个新问题：全场物品公开自身能力会泄露视野外信息。对执行器开放的全局物品注册表，不能直接作为角色决策输入。

## 3. 可直接评估的 Godot 组件

这些组件解决不同层次的问题，不应全部安装。表内版本范围来自当前作者资料，不是本机兼容性证明。

| 候选 | 可复用内容 | 接入成本与缺口 | 资料与许可 |
| --- | --- | --- | --- |
| Godot NavigationAgent | 路径查询、跟随辅助与避让 | 需要庭院导航区域与角色运动适配；节点不会自动移动身体，更不会自动处理脚滑和交互 | [官方文档](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationagents.html)，引擎 MIT |
| Beehave | 行为树、运行调试、成功/失败/运行中状态及中断接口 | 最接近现有 GDScript 工程的候选之一；移动、观察、交互仍由本项目实现 | [仓库](https://github.com/bitbrain/beehave)，MIT；兼容表为 Godot 4.5+ 对应 2.10+ |
| LimboAI | 行为树、层级状态机、Blackboard 与可视化调试 | 可用 GDExtension，不必定制引擎；需验证 Mac 二进制、版本与取消生命周期 | [仓库](https://github.com/limbonaut/limboai)，MIT；1.8.x 的扩展版注明 Godot 4.6+，模块版对应 4.7 |
| Godot State Charts | 状态转移、条件、延时、运行调试 | 适合控制权/行动阶段管理，不负责选择生活目标；只有现有状态管理确实复杂时才值得引入 | [仓库](https://github.com/derkork/godot-statecharts)，MIT 代码；示例中的图标另有 CC BY 许可 |
| Pennycook/godot-utility-ai | 按情境和响应曲线给候选行为评分 | 适合比较好奇、休息、继续旧目标等动机；具体动作与上下文仍需项目实现，Godot 4.7.2 兼容性待测 | [作者 README](https://github.com/Pennycook/godot-utility-ai)，插件 MIT，测试/示例 0BSD，标志 CC BY 4.0 |

源码核对带来的具体结论：Beehave 的 `BeehaveNode` 提供 `tick / interrupt / before_run / after_run`；其中基础 `interrupt` 只发调试信息，不会自动停止我们已有的导航、根位移或异步请求。接管时仍必须显式取消身体任务，并保留 `control_epoch` 校验。[源码](https://github.com/bitbrain/beehave/blob/godot-4.x/addons/beehave/nodes/beehave_node.gd)

LimboAI 的任务文档描述 `abort()` 会递归重置任务并退出正在运行的任务；我们的任务仍需在退出时清理外部执行器。文档页标题为 1.0，不能把接口说明直接当作 1.8 二进制验证，试装时需固定发行版并复核对应 API。[BTTask 文档](https://limboai.readthedocs.io/en/stable/classes/class_bttask.html)

建议先比较 Beehave 与 LimboAI 中的一种。Utility AI 是“当前更想做什么”的候选决策方法，行为树是“选中后怎么完成”的执行方法，两者可以组合，但组合不是前置要求。Beehave 作者也明确提醒简单 AI 使用行为树可能过度设计。

## 5. 什么样的体验值得研究

以下均为设计候选，尚未实施，也未由用户选择。可以使用同一庭院与同一套执行器比较。

### A. 她有自己的小事

她在水边看船，待一会儿又去别处停留；新变化可能吸引她，但不会每次立刻打断当前活动。研究重点是注意力持续、活动选择与节奏。少量内在变量和规则即可作为基线，不需要先引入饥饿条、经济系统或聊天。

### B. 你改变了她没看见的世界

她刚看过纸船，转身后你把船移走。她应先根据最后所见寻找，发现不同后再改变行动；若她亲眼看见移动，反应应不同。这个场景同时检查记忆、局部感知与行动反馈，也更容易让人读出角色“知道什么”。

### C. 默契地完成一件小事

她走到池边发现船过不去；你清除阻挡，船继续漂，她的注意力跟着变化。后续有合适动作再研究她亲手处理物体。研究重点是行为是否与玩家的干预产生可见联系，而非靠文字宣布“我注意到了你”。

暂时更值得深入的组合是 A+B：自主节奏与有限认知能够共用少量物体，又不必立即投入高成本手部抓取。C 保留为合作方向。此排序是设计判断，不是研究论文证明哪种更有趣。

## 6. 怎样判断资料已经足够支持下一步

后续按问题推进研究，而不是继续堆项目名称：

1. **行为执行选型**：固定一个 Beehave/LimboAI 发行版，在隔离工程运行“移动—观察—被打断”。比较取消是否彻底、可调试性、接现有动作的改动量。保持现有控制器，勿同时装两个框架。若简单状态机已经够用，允许不加依赖。
2. **人物交互复用核验**：检查 VirtualHome 可执行包的架构、许可和动作覆盖，挑一个真实日常活动，区分图状态成功与可见动画成功。若在 Mac 上运行成本过高，记录原因并转为源码/录像参考，不无限修旧依赖。
3. **认知与动机设计比较**：用同一个背后移物场景，设计固定规则、效用评分、LLM 高层选择三种策略的输入输出。先看现成方法能否解释我们想要的变化，再决定是否接入模型。
4. **体验评议**：呈现少量具体行为情境，让用户评价是否安静、是否能读懂、是否想继续干预。这一结果与技术正确性分别记录。

对比记录至少覆盖：看到/没看到干预的差异、绕路失败、目标丢失、人工接管、等待模型期间世界继续、重复尝试次数、实际调用耗时/费用（真实接入后才填写）。比较不同策略时保持可用动作和观察信息一致；全局真相只用于调试与检查。纯视觉作为后续单独变量，不能与换策略同时更换导致无法归因。

“有学习感”先分清三件事：带时间的事件记忆、可更新偏好、模型权重训练。前两者可以影响未来行为，均不自动等于强化学习。本轮不启动训练或 exploreBrain 集成。
